# 제4장: 코드 작성 전 탐색(Explore)과 증거 기반 계획(Plan)

---

## 1. 이 장의 결론

> **"계획 단계에서 발견된 오류를 수정하는 비용은 코드가 작성된 후 수정하는 비용의 1/100이다."**  
> 에이전트에게 구현 권한을 주기 전, **읽기 전용 탐색(Read-only Exploration)**을 통해 프로젝트 아키텍처를 파악하게 하고, 잠재적 실패를 예측하는 **프리모텀(Pre-mortem) 계획서**를 작성하게 해야 한다.

---

## 2. 이 문제가 중요한 이유

에이전트가 실패하는 주된 원인 중 하나는 '저장소의 전체 맥락을 모른 채 국소적인 파일 하나만 보고 섣불리 코드를 고치는 것'입니다.
특히 데이터베이스 스키마 변경, 전역 상태 관리, 공유 유틸리티 수정과 같은 고위험 작업에서는 연관된 수십 개의 파일과 런타임 제약 조건을 먼저 파악하지 않으면 대규모 장애로 이어집니다.

---

## 3. 핵심 개념

### 3.1 읽기 전용 탐색 (Read-only Exploration)
에이전트에게 파일 수정 도구(write/edit) 권한을 박탈하고, 오직 검색(grep/find)과 읽기(view/list) 도구만 부여하여 프로젝트의 호출 그래프(Call Graph)와 의존성을 파악하게 하는 절차.

### 3.2 프리모텀 분석 (Pre-mortem Analysis)
"이 변경사항이 배포 후 운영 DB를 멈추게 했다고 가정하자. 원인이 무엇이었겠는가?"를 에이전트에게 스스로 역추적하게 하여 사전 방어 대책을 계획에 포함시키는 기법.

---

## 4. 잘못된 접근 사례

### [사례 5: DB 스키마 마이그레이션] - 즉각적 구현의 위험
- **지시문**: *"User 테이블에 `nickname` 컬럼 추가하고 유니크 인덱스 걸어줘."*
- **참사 발생**:
  - 에이전트가 `ALTER TABLE users ADD COLUMN nickname VARCHAR(50) NOT NULL UNIQUE;` 마이그레이션 파일을 즉시 생성함.
  - 기존 수백만 건의 레코드가 존재하는 프로덕션에 배포 시, `NOT NULL` 제약조건으로 인해 배포 실패 및 테이블 풀락(Full Table Lock) 발생.

---

## 5. 개선된 접근 사례

### 사전 탐색 및 3단계 무중단 마이그레이션 계획 수립

1. **사전 탐색 단계**:
   - 에이전트가 기존 `users` 테이블 정의와 마이그레이션 히스토리, ORM 엔티티 파일들을 전수 조사.
2. **프리모텀 계획 제출**:
   - 위험 요소 파악: "기존 데이터가 있는 상태에서 NOT NULL + UNIQUE를 한 번에 걸면 마이그레이션이 실패하거나 서비스가 중단됨."
   - 3단계 무중단 전환 계획 수립:
     - 1단계: Nullable 컬럼 추가 (`nickname VARCHAR(50) NULL`)
     - 2단계: 백그라운드 데이터 마이그레이션 및 기본값 채우기
     - 3단계: 유니크 인덱스 비동기 생성 (`CREATE UNIQUE INDEX CONCURRENTLY`) 및 NOT NULL 제약조건 추가.
     - 4단계: 다운타임 없는 롤백(Rollback) 스크립트 선행 준비.

---

## 6. 실제 작업 프롬프트

템플릿 4와 5를 결합하여 에이전트에게 주입합니다:

```markdown
당신은 수석 DBA 겸 데이터 아키텍트입니다.
`User` 엔티티에 닉네임 필드를 추가하려 합니다.

[작업 지시]
1. 코드를 작성하지 마십시오. 기존 `prisma/migrations/` 또는 `src/entities/` 디렉토리를 탐색하십시오.
2. 기존 데이터 보존, 인덱스 락(Lock) 위험, 무중단 롤백을 고려한 [사전 계획서]를 작성하십시오.
3. 계획서에 '실패 시 롤백 SQL 스크립트'를 반드시 포함하십시오.
```

---

## 7. 에이전트가 제출해야 할 증거

- [탐색 보고서]: 기존 DB 마이그레이션 파일 목록 및 ORM 엔티티 정의 요약.
- [마이그레이션 계획서]: Up SQL, Down(Rollback) SQL, 락 최소화 방안.

---

## 8. 사람이 확인할 사항

- [ ] 롤백(Down) 스크립트가 데이터 유실 없이 안전하게 복구 가능한가?
- [ ] 대용량 테이블에 대한 락 유발 쿼리(`CONCURRENTLY` 누락 등)가 없는가?
- [ ] 기존 애플리케이션 코드가 마이그레이션 과도기 상태를 지원하는가?

---

## 9. 팀 적용 방법

- **DB 변경에 대한 자동 게이트 (Schema Review Gate)**: CI 파이프라인에서 마이그레이션 파일 추가가 감지되면, 무조건 DBA 또는 테크리드의 사전 승인이 있어야 머지되도록 규칙 설정.
