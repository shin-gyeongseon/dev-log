### 사례 1: 단순 CRUD 기능

* **단순 요청**: *"사용자 생성 API랑 테스트 만들어줘."*
* **개선된 작업 명세 (4단 명세)**:
  * **Req**: `POST /users` (이름, 나이, 이메일). 이메일 형식 불일치 또는 나이 음수 시 HTTP 400.
  * **Const**: `src/users/` 하위만 수정. Zod 유효성 검증 라이브러리 사용.
  * **DoD**: 성공(201), 이메일오류(400), 음수나이(400) 3종 단위 테스트 및 DB 영속화 검증.
  * **Anti-Goals**: JWT 인증이나 권한 로직은 추가하지 말 것.
* **잘못된 테스트**: `expect(res).toBeDefined();` (단언문 부실, 음수 나이도 통과)
* **개선된 테스트**:
  ```typescript
  await expect(service.createUser({ name: '홍길동', age: -5, email: 'a@b.com' }))
    .rejects.toThrow(InvalidAgeException);
  ```
* **에이전트의 잘못된 성공 보고**: *"사용자 생성 기능과 테스트를 완벽히 구현하여 통과했습니다."*
* **증거 중심의 최종 보고**: `npm test tests/users/create.test.ts` 원본 로그(성공/실패 3종 통과), Git diff 45줄.
* **사람의 승인 여부와 이유**: **승인 (Tier 2)** - 네거티브 검증이 명확하고 기존 회귀 없음.

### 사례 2: 외부 API 연동

* **단순 요청**: *"토스페이먼츠 결제 승인 API 연동해줘."*
* **개선된 작업 명세**: 외부 API 응답을 Zod Schema로 런타임 유효성 검증. 타임아웃 3초, 실패 시 커스텀 예외 매핑.
* **잘못된 테스트**: `mockResolvedValue({ status: 'OK' })` (실제 PG사 스키마와 다른 가짜 객체 모킹)
* **개선된 테스트**: WireMock 기반으로 계약 위반 응답(JSON 키 누락) 주입 시 `SchemaValidationError` 발생 검증.
* **에이전트의 잘못된 성공 보고**: *"결제 API Mock 테스트가 100% 성공했습니다."*
* **증거 중심의 최종 보고**: 실제 API 스키마 일치 증명 및 WireMock 4종 시나리오(성공, 잔액부족, 타임아웃, 스키마불일치) 통과 로그.
* **사람의 승인 여부와 이유**: **승인 (Tier 3 사전 승인 후 진행)** - 계약 스키마 검증 완비.

### 사례 3: 인증 및 권한 기능 (RBAC)

* **단순 요청**: *"관리자만 접근할 수 있는 미들웨어 만들어줘."*
* **개선된 작업 명세**: `requireRole(['ADMIN'])`. 미인증은 401, 권한부족은 403. 보안 감사 로그 기록.
* **잘못된 테스트**: 권한이 없을 때 500 에러를 던지는데도 `toBeFalsy()`로 대충 퉁치고 통과시킴.
* **개선된 테스트**: 401과 403의 HTTP 상태 코드 및 감사 로거 호출 인자(`userId`, `role`) 정확히 Assert.
* **에이전트의 잘못된 성공 보고**: *"RBAC 미들웨어 구현 완료!"*
* **증거 중심의 최종 보고**: 3대 HTTP 상태 코드 분기 증적 및 보안 감사 로그 출력 캡처.
* **사람의 승인 여부와 이유**: **승인 (Tier 3)** - 보안 로깅 및 권한 분기 완벽 증명.

### 사례 4: 기존 버그 수정

* **단순 요청**: *"장바구니 10만원 이상 할인 안 먹는 버그 고쳐줘."*
* **개선된 작업 명세**: 경계값(100,000원)에서 버그를 재현하는 Failing First 테스트 선행 작성 후 최소 수정.
* **잘못된 테스트**: 버그를 고치기 전에도 통과하던 쓸모없는 테스트 작성.
* **개선된 테스트**: Red $\rightarrow$ Green 사이클 입증 및 변이 테스트(돌연변이 사망 증명).
* **에이전트의 잘못된 성공 보고**: *"할인 버그를 수정하여 정상 동작합니다."*
* **증거 중심의 최종 보고**: 수정 전 실패(Expected 90000, Received 100000) 로그 + 수정 후 통과 로그 + 변이 테스트 결과.
* **사람의 승인 여부와 이유**: **승인 (Tier 2)** - 실패 증명이 명확하여 회귀 위험 없음.

### 사례 5: 데이터베이스 스키마 변경

* **단순 요청**: *"User 테이블에 닉네임 유니크 컬럼 추가해줘."*
* **개선된 작업 명세**: 사전 탐색 $\rightarrow$ 프리모텀 분석 $\rightarrow$ 3단계 무중단 DDL(Nullable 추가 $\rightarrow$ 백필 $\rightarrow$ 유니크 인덱스 생성) $\rightarrow$ 롤백 SQL 작성.
* **잘못된 테스트**: 인메모리 SQLite에서 `NOT NULL UNIQUE` 바로 넣고 통과했다고 보고.
* **개선된 테스트**: 기존 100만 건 데이터가 존재하는 환경에서 락 시간 및 롤백 스크립트 실행 무결점 검증.
* **에이전트의 잘못된 성공 보고**: *"마이그레이션 파일 생성을 완료했습니다."*
* **증거 중심의 최종 보고**: Up/Down 마이그레이션 멱등성 검증 로그 및 롤백 성공 로그.
* **사람의 승인 여부와 이유**: **인간 사전 승인 필수 (Tier 3)** - DBA 검토 후 실행 승인.

### 사례 6: 프런트엔드 사용자 흐름

* **단순 요청**: *"결제 완료 페이지 만들고 플로우 테스트해줘."*
* **개선된 작업 명세**: Playwright 헤드리스 브라우저로 장바구니 담기 $\rightarrow$ 주문서 작성 $\rightarrow$ 결제 완료 텍스트 및 DOM 검증 $\rightarrow$ 스크린샷 캡처.
* **잘못된 테스트**: Jest 스냅샷으로 렌더링 여부만 검사 (실제 클릭 불능 감지 못함).
* **개선된 테스트**: 실제 브라우저 클릭 이벤트 및 콘솔 에러 0건, 스크린샷 아티팩트 생성.
* **에이전트의 잘못된 성공 보고**: *"프론트엔드 UI 작업이 끝났습니다."*
* **증거 중심의 최종 보고**: Playwright 실행 결과 로그 및 `artifacts/checkout-complete.png` 스크린샷 제출.
* **사람의 승인 여부와 이유**: **승인 (Tier 2)** - 시각적 스크린샷으로 레이아웃 정상 확인.

### 사례 7: 비동기 또는 동시성 처리

* **단순 요청**: *"선착순 쿠폰 발급 기능 만들어줘."*
* **개선된 작업 명세**: Redis 분산 락 또는 DB 비관적 락(`SELECT FOR UPDATE`) 적용. 100개 동시 요청 시 정확히 10개만 발급 보장.
* **잘못된 테스트**: 단일 루프에서 1개씩 순차 호출(Sequential)하고 통과 판정.
* **개선된 테스트**: `Promise.all`로 100개 스레드 동시 발송 스트레스 테스트.
* **에이전트의 잘못된 성공 보고**: *"쿠폰 발급 로직 구현 완료."*
* **증거 중심의 최종 보고**: 동시 100회 요청 시 `10 fulfilled, 90 rejected`, 최종 발급 수량 10건 일치 로그.
* **사람의 승인 여부와 이유**: **승인 (Tier 3)** - Race condition 없음 입증.

### 사례 8: 성능 개선

* **단순 요청**: *"유저 목록 조회 API 빠르게 최적화해줘."*
* **개선된 작업 명세**: N+1 쿼리 해결 (JOIN FETCH) 및 페이징 적용. 전역 메모리 캐싱 금지.
* **잘못된 테스트**: 자바스크립트 전역 변수에 무제한 캐싱하고 속도 빨라졌다고 보고 (OOM 위험).
* **개선된 테스트**: 독립 레드팀 에이전트의 메모리 릭 감사 + DB 쿼리 카운트 1회 단언.
* **에이전트의 잘못된 성공 보고**: *"응답 속도가 99% 빨라졌습니다."*
* **증거 중심의 최종 보고**: 쿼리 발생 횟수($101 \rightarrow 1$회) 증적 및 독립 레드팀의 APPROVED 판정문.
* **사람의 승인 여부와 이유**: **승인 (Tier 2)** - 메모리 누수 없이 쿼리 최적화 확인.

### 사례 9: 운영 장애 조사

* **단순 요청**: *"500 에러 계속 나는데 왜 그런지 찾아줘."*
* **개선된 작업 명세**: 운영 로그 트레이싱 $\rightarrow$ 에러 재현 최소 스크립트 작성 $\rightarrow$ 근본 원인(Root Cause) 보고서 제출 $\rightarrow$ 핫픽스 격리 브랜치 생성.
* **잘못된 테스트**: 에러 로그도 안 보고 아무 코드나 `try-catch`로 감싸서 에러를 삼켜버림.
* **개선된 테스트**: 장애 원인이 된 Null 역참조 시나리오를 단위 테스트로 재현 후 패치.
* **에이전트의 잘못된 성공 보고**: *"에러가 더 이상 발생하지 않습니다."*
* **증거 중심의 최종 보고**: 근본 원인 분석 보고서 + 재현 테스트 실패/성공 로그.
* **사람의 승인 여부와 이유**: **승인 (Tier 2)** - 근본 원인 규명 및 영구 회귀 방지 확보.

### 사례 10: 장시간 무인 작업 (Overnight)

* **단순 요청**: *"퇴근할 테니까 밤새 레거시 코드 정리하고 테스트 채워놔."*
* **개선된 작업 명세**: 템플릿 13 적용 (재시도 3회 제한, 수정 파일 5개 제한, 금지 명령 차단, 모닝 리포트 생성).
* **잘못된 테스트**: 밤새 빌드 에러를 고치려다 수십 개 파일을 무차별 삭제하고 전체 프로젝트 파괴.
* **개선된 테스트**: 격리 브랜치에서 안전하게 작업하고, 실패한 항목은 보류(Quarantine) 처리.
* **에이전트의 잘못된 성공 보고**: 아침에 아무런 보고서 없이 에러 화면만 띄워져 있음.
* **증거 중심의 최종 보고**: 템플릿 14 형식의 모닝 리포트(완료 3건, 보류 1건, 커버리지 +5.7%p 상승 증적).
* **사람의 승인 여부와 이유**: **승인 및 인계** - 출근 후 3분 만에 성공 항목 병합 및 보류 항목 의사결정.
