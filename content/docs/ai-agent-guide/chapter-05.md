# 제5장: 테스트 자체를 의심하라: 네거티브 테스트와 변이 검증

---

## 1. 이 장의 결론

> **"실패해 본 적 없는 테스트는 신뢰할 수 없다."**  
> 에이전트가 작성한 테스트 코드의 진정한 신뢰성은 **1) 버그를 재현하여 먼저 실패(Red)하는 증거**와 **2) 의도적인 코드 돌연변이(Mutation)를 주입했을 때 테스트가 이를 감지해 내는 능력(Killed Mutants)**으로 증명된다.

---

## 2. 이 문제가 중요한 이유

버그 수정(Bugfix)을 에이전트에게 요청할 때 가장 흔히 겪는 실패는 다음과 같습니다:
1. 에이전트가 버그의 근본 원인을 고치지 않고, 버그를 우회하는 엉뚱한 방어 코드를 작성함.
2. 테스트를 추가했다고 보고하지만, 그 테스트는 버그가 수정되기 전에도 이미 통과(Green)하던 쓸모없는 테스트였음.
3. 결과적으로 버그는 전혀 해결되지 않은 채 프로덕션에 그대로 남아 있게 됨.

이러한 문제를 방지하기 위해서는 **"테스트가 실제로 실패할 수 있는 능력이 있는가?"**를 수학적/실험적으로 검증해야 합니다.

---

## 3. 핵심 개념

### 3.1 네거티브 선행 검증 (Failing First Principle)
기존 버그를 수정할 때, **"구현 코드를 고치기 전에 먼저 현재 코드베이스에서 실패하는 테스트 케이스를 작성하여 실행 로그(Red)를 제출"**하도록 강제하는 원칙.

### 3.2 변이 테스트 (Mutation Testing)
소스 코드에 의도적으로 결함(비교 연산자 반전, 경계값 변경, 반환값 누락 등)을 주입(Mutation)한 후 테스트 슈트를 실행하는 기법.
- **돌연변이 사망 (Mutant Killed)**: 테스트가 실패함 $\rightarrow$ 테스트가 해당 결함을 정상적으로 잡아냄 (성공).
- **돌연변이 생존 (Mutant Survived)**: 코드가 망가졌는데도 테스트가 통과함 $\rightarrow$ 테스트의 단언문 부실 또는 맹점 존재 (실패).

$$\text{변이 점수 (Mutation Score)} = \frac{\text{사망한 돌연변이 수 (Killed)}}{\text{전체 돌연변이 수 (Total Mutants)}} \times 100\%$$

---

## 4. 잘못된 접근 사례

### [사례 4: 장바구니 할인 계산 버그 수정] - 가짜 버그 수정
- **현상**: 10만 원 이상 구매 시 10% 할인이 적용되어야 하나 적용되지 않는 버그 발생.
- **에이전트의 잘못된 행동**:
  - 버그 원인인 할인 조건 연산자(`>` vs `>=`)를 고치는 대신, 함수 반환값에 무조건 10,000원을 빼버리는 하드코딩 패치를 적용.
  - 테스트 코드는 10만 원 케이스만 검증하여 통과했다고 보고. (5만 원 구매 고객도 10,000원 할인되는 치명적 회귀 버그 발생)

---

## 5. 개선된 접근 사례

### 3단계 증거 기반 버그 수정 및 변이 검증

```typescript
// 1단계: 실패하는 재현 테스트 선행 작성 (Failing First)
describe('DiscountCalculator Bug Reproduction', () => {
  it('정확히 100,000원 구매 시 10% 할인이 적용되어 90,000원을 반환해야 한다', () => {
    const calc = new DiscountCalculator();
    // 현재 코드에서는 100,000원 초과(>)만 할인되어 100,000원이 반환됨 -> RED 확인!
    expect(calc.calculateFinalPrice(100000)).toBe(90000);
  });
  
  it('99,999원 구매 시 할인이 적용되지 않고 99,999원을 반환해야 한다 (회귀 방지)', () => {
    const calc = new DiscountCalculator();
    expect(calc.calculateFinalPrice(99999)).toBe(99999);
  });
});
```

* **수행 절차**:
  1. 위 테스트를 실행하여 `100000 !== 90000` 실패 로그 제출.
  2. 비즈니스 로직 수정 (`price >= 100000`).
  3. 테스트 통과 (Green) 확인.
  4. 변이 테스트: `price >= 100000`을 `price > 100000`으로 돌연변이 주입 시 위 테스트가 실패하는지(Killed) 증명.

## 6. 실제 작업 프롬프트

```markdown
당신은 엄격한 TDD 수석 QA 엔지니어입니다.
장바구니 할인 계산 버그를 수정하십시오.

[필수 이행 절차]
1. [Red 단계]: 기존 코드를 전혀 수정하지 말고, 버그를 재현하여 실패하는 테스트 케이스를 먼저 작성하십시오. 실패 실행 로그(Terminal output)를 제출하십시오.
2. [Green 단계]: 버그를 유발하는 최소한의 비즈니스 로직을 수정하고, 모든 테스트가 통과하는 로그를 제출하십시오.
3. [Mutation 단계]: 수정된 코드의 경계값을 의도적으로 1군데 변조한 뒤 테스트가 실패하여 돌연변이를 잡아냄(Killed)을 증명하십시오.
```

---

## 7. 에이전트가 제출해야 할 증거

- [증거 1]: 버그 재현 테스트 실패 원본 로그 (`Expected 90000, Received 100000`).
- [증거 2]: 버그 수정 후 테스트 통과 로그.
- [증거 3]: 수동 또는 자동 변이 테스트 결과표 (Mutant Killed 증적).

---

## 8. 사람이 확인할 사항

- [ ] 에이전트가 버그 수정 전에 제출한 실패 로그가 진짜 해당 버그를 재현하고 있는가?
- [ ] 경계값(Boundary value: 99,999원 / 100,000원 / 100,001원) 테스트가 모두 포함되었는가?
- [ ] 하드코딩된 매직 넘버 패치가 없는가?
