# 실전 템플릿 팩 1: 작업 요청 및 명세 템플릿

이 문서에는 AI 에이전트에게 모호함 없이 작업을 위임하기 위한 3종의 핵심 명세 템플릿이 포함되어 있습니다.

---

## 템플릿 1: 4단 작업 명세서 (The 4-Part Task Specification)

* **사용 목적**: 에이전트가 자의적으로 요구사항을 추측하거나 범위를 벗어나는 작업을 방지.
* **사용 시점**: 모든 신규 기능 개발, 버그 수정, 리팩토링 요청 시.
* **필수 입력**: 기능 개요, 비즈니스 규칙, 제약 사항, 완료 판정 기준.

```markdown
# [작업 명세] {기능 또는 작업명}

## 1. 요구사항 (Requirements)
- [ ] {요구사항 1}: 사용자는 {입력값}을 제공하여 {원하는 결과}를 얻을 수 있어야 한다.
- [ ] {요구사항 2}: {조건}일 때 시스템은 {구체적 동작}을 수행해야 한다.
- [ ] {엣지 케이스}: 잘못된 형식 입력 시 HTTP 400 및 표준 에러 메시지(`{ "error": "INVALID_FORMAT" }`)를 반환해야 한다.

## 2. 제약조건 (Constraints)
- **아키텍처/패턴**: 기존 `{폴더/모듈명}`의 계층 구조를 준수할 것. 새 외부 라이브러리 추가 금지 (기존 `zod`, `axios` 등만 사용).
- **수정 허용 범위**: `src/features/{domain}/` 하위 파일만 수정 가능. 공통 설정 파일(`tsconfig.json`, `package.json`) 수정 금지.
- **성능/자원**: 단일 요청 처리 시간 p99 < 200ms, DB 쿼리 수 2회 이내 (N+1 방지).

## 3. 완료 정의 (Definition of Done - DoD)
- [ ] **구현 증명**: 대상 기능의 핵심 비즈니스 로직 단위 테스트 통과.
- [ ] **네거티브 증명**: 잘못된 인자 전달 시 의도한 예외가 발생하는 테스트 증거 제출.
- [ ] **기존 회귀 방지**: 전체 테스트 슈트(`npm test`) 실행 결과 회귀 없음 (0 failures).
- [ ] **최소 증거 제출**: 실행된 테스트 명령, 결과 로그, 수정된 파일의 git diff 목록 제출.

## 4. 금지사항 (Anti-Goals / Out of Scope)
- ❌ UI 디자인 개편이나 스타일 리팩토링은 절대 하지 말 것.
- ❌ 이번 작업에서 결제 PG사 실서버 연동은 다루지 않음 (인터페이스 및 Mock까지만 작성).
- ❌ 기존에 통과하던 테스트를 주석 처리하거나 완화하여 통과시키지 말 것.
```

## 템플릿 2: 완료 조건(DoD) 및 비완료 조건(Anti-DoD) 상세 판정표

* **사용 목적**: 에이전트가 "동작은 하지만 불완전한 상태"를 완료라고 우기는 것을 원천 차단.

```markdown
### ✅ 완료 조건 (Definition of Done)
1. **코드 품질**: Lint 검사(`npm run lint`) 에러 0건, 타입 검사(`tsc --noEmit`) 에러 0건.
2. **테스트 충실도**: 추가된 비즈니스 로직에 대해 성공/실패/경계값 테스트 케이스 3종 이상 포함.
3. **가역성 (Reversibility)**: 단일 커밋으로 안전하게 되돌릴(revert) 수 있는 독립적 변경 단위.
4. **증거 첨부**: 터미널 실행 로그 캡처 및 변경 전후 테스트 통과 diff 첨부.

### ❌ 비완료 조건 (Anti-DoD - 다음 항목 중 하나라도 해당 시 작업 실패 판정)
1. 기존 테스트가 실패하자 테스트 단언문(assert) 값을 임의로 고친 경우.
2. `any` 타입을 남발하거나 `@ts-ignore`, `eslint-disable`을 임의 추가한 경우.
3. 외부 네트워크 의존성을 제거하지 않고 로컬 환경에서만 성공하는 불안정한 테스트를 작성한 경우.
4. 요구하지 않은 주변 레거시 파일들을 임의로 리팩토링하여 diff가 200줄을 초과한 경우.
```

## 템플릿 3: 에이전트 질문 유도 및 가정 통제 프롬프트

* **사용 목적**: 에이전트가 중요한 의사결정을 자의적으로 가정하지 않고 인간에게 명확히 질의하게 만듦.

```markdown
당신은 수석 엔지니어로서 본 작업을 수행합니다.
작업을 진행하기 전, 다음 규칙을 엄격히 준수하십시오:

1. [질문 조건]: 다음 상황에 해당하면 코드를 작성하지 말고 즉시 멈추어 사용자에게 질문하십시오.
   - 기존 코드베이스 내에서 상충되는 비즈니스 로직이 발견된 경우
   - 데이터베이스 스키마 변경 시 기존 데이터 유실 위험이 있는 경우
   - 명세에 정의되지 않은 외부 API 응답 규격이 필요한 경우
   
2. [가정 허용 조건]: 다음 범위 내에서는 스스로 최선의 관례를 가정하고 계획서에 명시한 뒤 진행하십시오.
   - 내부 변수명, 비공개 헬퍼 함수명 명명 규칙
   - 표준적인 단위 테스트 디렉토리 위치 (`__tests__/`)
   - 기존 프로젝트에서 이미 사용 중인 유틸리티 함수 활용
```
