# 실전 템플릿 팩 2: 사전 조사 및 구현 계획 프롬프트

---

## 템플릿 4: 저장소 아키텍처 탐색 및 영향도 조사 프롬프트

* **사용 목적**: 코드를 섣불리 수정하기 전, 에이전트가 기존 프로젝트의 파일 구조, 의존성, 컨벤션을 읽기 전용 모드로 정밀 분석하게 유도.

```markdown
당신은 시스템 아키텍트입니다. 현재 작업 공간에서 다음 지침에 따라 [사전 탐색]을 수행하십시오.
코드를 수정하거나 파일을 생성하지 마십시오. 오직 분석 결과만을 보고하십시오.

### 탐색 지시사항
1. 대상 기능과 관련된 파일 및 디렉토리 구조를 파악하십시오.
2. 현재 프로젝트에서 사용 중인 테스트 프레임워크, 상태 관리, 유효성 검증 라이브러리를 확인하십시오.
3. 대상 코드를 참조하고 있는 외부 파일(호출자, Callers) 목록을 추출하십시오.
4. 이 변경으로 인해 영향을 받을 수 있는 잠재적 위험 지점 3가지를 명시하십시오.

### 출력 형식
- [관련 파일 목록]: `경로` (역할)
- [기존 패턴 및 컨벤션]: 확인된 네이밍/계층 규칙
- [영향 범위(Blast Radius)]: 고/중/저 및 근거
- [탐색 중 발견된 특이사항]:
```

## 템플릿 5: 프리모텀(Pre-mortem) 기반 구현 계획서 템플릿

* **사용 목적**: "구현이 실패한다면 왜 실패할 것인가?"를 사전에 에이전트 스스로 예측하여 안전장치를 마련하게 함.

```markdown
# [구현 계획] {작업명}

## 1. 해결하려는 문제 및 배경
{현재 상태와 변경 후 목표 상태 요약}

## 2. 사전 실패 분석 (Pre-Mortem Analysis)
> "이 작업이 배포 후 심각한 버그를 일으켰다면, 가장 유력한 원인은 무엇인가?"
- **위험 가설 1**: {예: 기존 캐시 무효화가 누락되어 낡은 데이터 반환}
  - **대응 방안**: 캐시 무효화 로직 단위 테스트 및 TTL 검증 추가
- **위험 가설 2**: {예: 대용량 데이터 입력 시 메모리 초과}
  - **대응 방안**: 스트리밍 처리 및 페이지네이션 제약 적용

## 3. 단계별 수정 계획 (Step-by-Step Implementation)
- **1단계: 검증 테스트 선행 작성 (Failing First)**
  - 대상 파일: `tests/{domain}/{name}.test.ts`
  - 기대 동작: 현재 코드로 실행 시 실패(Red) 확인
- **2단계: 최소 비즈니스 로직 구현**
  - 수정 대상: `src/{domain}/{file}.ts`
  - 변경 사항: {구체적 수정 명세}
- **3단계: 통합 검증 및 회귀 테스트**
  - 검증 명령: `npm test -- {test-path}`

## 4. 롤백 계획 (Rollback Strategy)
- 문제 발생 시 되돌릴 커밋 및 복구 절차: `git revert HEAD` 후 기존 스키마 호환 유지
```

## 템플릿 6: 테스트 전략 수립 프롬프트

```markdown
다음 요구사항에 대해 [테스트 전략]을 수립하십시오.
테스트는 다음 3계층 피라미드 구조를 만족해야 합니다:

1. **단위 테스트 (Unit)**: 핵심 비즈니스 계산식, 순수 함수, 상태 전이 규칙 (목킹 최소화).
2. **통합 테스트 (Integration)**: DB 쿼리, ORM 매핑, 외부 서비스 계약 검증 (인메모리 또는 컨테이너).
3. **네거티브/엣지 테스트 (Negative & Edge)**: Null/Undefined, 최대 경계값, 인증 실패, 타임아웃.

각 계층별로 최소 2개 이상의 구체적 테스트 시나리오와 예상 단언문(Expectation)을 표로 제시하십시오.
```
